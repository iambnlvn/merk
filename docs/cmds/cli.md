# merk CLI Reference

`merk` is a git-like version control system written in Zig. It tracks files in
a **staging area**, records them into immutable **commits** on a **track**
(merk's branch equivalent), and stores content-addressed objects under a
`.merk` control directory in the repository root.

> to rely on it

> This document is a complete reference for every command currently exposed by
> the CLI, generated from the command implementations themselves (flag
> definitions, validation logic, and success/error output).

## Conventions used below

- `<...>` — required argument
- `[...]` — optional argument or flag
- `...` — the preceding argument may repeat
- Flags shown as `-x, --long-name` support both forms; flags with only a long
  form have no short alias.
- Every command that touches an existing repository resolves the repository
  root the same way (walking up from the working directory to find `.merk`);
  this is omitted from each entry for brevity.
- Exit behavior: commands print a human-readable `error: ...` message to
  stderr and return a non-zero exit status on failure. Where a command has
  notable failure modes, they're listed under **Errors**.

## `merk init`

Initialize a new merk repository.

### Synopsis

```
merk init [directory] [-q|--quiet] [-f|--force]
```

### Description

Creates a `.merk` control directory inside `directory` (default: the current
directory, `.`) and initializes empty repository state — an empty staging
area and no track history. If `.merk` already exists, `init` refuses to
touch it unless `--force` is passed, in which case the repository is
**reinitialized**: the current focus and the staging index are reset to
empty. Reinitializing does _not_ delete existing commit/object data — history
made under the old state remains content-addressed in the object store, it's
just no longer reachable from the reset track pointer.

### Options

| Flag          | Description                                                                        |
| ------------- | ---------------------------------------------------------------------------------- |
| `-q, --quiet` | Only print errors and warnings; suppress the success banner and "next steps" hint. |
| `-f, --force` | Reinitialize an already-initialized repository instead of failing.                 |

### Examples

Initialize a repository in the current directory:

```console
$ merk init
Initialized merk repository in /home/user/projects/my-app

Next steps:
  merk stage --all
  merk commit -m "Initial commit"
```

Initialize a repository in a new subdirectory:

```console
$ merk init my-project
Initialized merk repository in /home/user/projects/my-project

Next steps:
  cd my-project
  merk stage --all
  merk commit -m "Initial commit"
```

Reinitialize (reset) an existing repository:

```console
$ merk init --force
Reinitialized merk repository in /home/user/projects/my-app
The existing repository state was reset.

Next steps:
  merk stage --all
  merk commit -m "Initial commit"
```

### Errors

- Running `init` against an already-initialized repository without `--force`
  prints `error: repository already initialized` with a hint to use
  `--force`, and exits without modifying anything.

## `merk stage`

Stage changes from one or more paths.

### Synopsis

```
merk stage [-A|--all] [-n|--dry-run] [-p|--patch] [--context <n>] [<path>|<dir>...]
```

### Description

`stage` is merk's equivalent of `git add`. It moves the current on-disk
content of the given paths into the staging area so that a subsequent
`commit` records it.

- Passing plain file paths stages exactly those files.
- Passing a directory (or `.`) recursively walks it and stages **every**
  file underneath — including files that have never been tracked before.
  The `.merk` control directory is always skipped during the walk.
- `--all` restages every **already-tracked** path that currently shows as
  `Modified` in `status`. It does **not** discover brand-new files (use a
  directory argument or `.` for that), and it does not currently stage
  deletions.
- Duplicate paths (whether typed twice, or reachable both directly and via a
  directory argument) are staged only once.
- Output is sorted lexicographically by path for deterministic, scriptable
  results regardless of filesystem walk order.

If a given path doesn't exist on disk, `stage` prints an error and — as a
convenience — scans currently tracked paths for a similarly-named entry
(matching basename or substring) and suggests up to three "did you mean"
candidates.

### Options

| Flag            | Description                                                                                                                                     |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `-A, --all`     | Restage every already-tracked path with a pending modification. Combine with a directory path (or `.`) to also pick up new, never-staged files. |
| `-n, --dry-run` | Preview what would be staged (`added` vs `updated`) without making any changes.                                                                 |
| `-p, --patch`   | Interactively choose which hunks to stage, file by file. Mutually exclusive with `--dry-run`.                                                   |
| `--context <n>` | Lines of context shown around each hunk in `--patch` mode. Default: `3`.                                                                        |

### Examples

Stage a single file:

```console
$ merk stage src/main.zig
stage    src/main.zig

1 path staged
```

Stage everything under the current directory (new and modified files):

```console
$ merk stage .
stage    src/args.zig
stage    src/main.zig
update   README.md

3 paths staged
```

Restage every already-tracked file with pending edits, without picking up
new files:

```console
$ merk stage --all
update   src/main.zig

1 path staged
```

Preview what would be staged, without staging it:

```console
$ merk stage --dry-run src/
would stage   src/args.zig
would update  src/main.zig
```

Interactively stage hunks from a file:

```console
$ merk stage --patch --context 5 src/main.zig
```

### Notes

- `stage` reports `added` (path newly tracked) vs `updated` (path already
  tracked, content changed) for each path — both in normal and `--dry-run`
  output — so you always know which case you're in without a separate
  `status` call.
- If nothing matches the given paths, or every discovered file is
  unchanged, `stage` prints `nothing to stage` and exits successfully.

### Errors

- A nonexistent path aborts the whole invocation with `error: path '<p>'
does not exist` (after validating _all_ given paths, so partial staging
  from a typo-laden invocation doesn't happen silently).
- `--dry-run` and `--patch` together: `error: --dry-run and --patch are
mutually exclusive`.

## `merk status`

Show the repository status.

### Synopsis

```
merk status
```

### Description

Prints a summary of the repository's pending changes in two groups:

- **Staged for next commit** — paths whose staged content differs from the
  current track tip (what `merk commit` would record).
- **Modified** / **Deleted** — working-tree paths that differ from what's
  currently staged (not yet staged).

Takes no arguments or flags.

### Examples

Clean repository:

```console
$ merk status
Repository

No pending snapshot.
Working tree is clean.
```

Repository with both staged and unstaged changes:

```console
$ merk status
Repository

Staged for next commit (2 paths)

Modified
  src/main.zig

Deleted
  old_module.zig
```

## `merk diff`

Show changes between staging and the working tree, or between commits with
`--rev`.

### Synopsis

```
merk diff [options] [<path>...]
```

### Description

By default, `diff` compares the **working tree against the staging area**
(i.e. "what would `merk stage` pick up") on a line-by-line basis for every
staged path whose on-disk content has changed.

Pass `--rev` to compare commits instead:

- **Zero `--rev` flags** (default): working tree vs. staging.
- **One `--rev <hash>`**: that commit against its first parent.
- **Two `--rev <hash>` flags** (repeatable): the first revision against the
  second, in the order given.
- `--rev` also accepts comma-separated hashes in a single flag occurrence
  (`--rev a1b2c3,d4e5f6`), and both full 64-character hashes and 8+ character
  prefixes are accepted.
- `--staged` shows a structural (Merkle-tree) summary of staged changes —
  the same data `status` uses under "Staged" — rather than a full line-level
  diff. It's mutually exclusive with `--rev`.

Positional arguments restrict the diff to paths under the given prefixes.

### Options

| Flag                 | Description                                                                    |
| -------------------- | ------------------------------------------------------------------------------ |
| `-f, --format <fmt>` | `unified`, `side-by-side`, `blocks`, `ops`, `summary`                          |
| `-l, --level <lvl>`  | `file`, `hunk`, `line`, `word`                                                 |
| `-c, --context <n>`  | Context lines: an integer, or `minimal`, `normal`, `full`                      |
| `-g, --group <mode>` | `none`, `files`, `dirs`                                                        |
| `--algo <name>`      | `myers`, `patience`, `histogram` (default: `histogram`)                        |
| `--rev <hash>`       | Commit to compare; repeat for two commits                                      |
| `--word`             | Enable inline word-level highlighting                                          |
| `--only-added`       | Show only added files                                                          |
| `--only-deleted`     | Show only deleted files                                                        |
| `--only-modified`    | Show only modified files                                                       |
| `--show <types>`     | Comma-separated subset: `added,deleted,modified`                               |
| `--detect-moves`     | Heuristic move/rename detection                                                |
| `--no-color`         | Disable ANSI color                                                             |
| `--color <when>`     | `auto` (default), `always`, `never` — overrides `--no-color` if both are given |
| `--profile <name>`   | Apply a bundle of settings; see below                                          |
| `--staged`           | Summarize staged changes structurally (mutually exclusive with `--rev`)        |
| `--working`          | Diff the working tree (default; accepted as an explicit no-op)                 |

**Profiles** (`--profile`) set several options at once:

| Profile  | Effect                                             |
| -------- | -------------------------------------------------- |
| `review` | `format=side-by-side`, `level=line`, `group=files` |
| `ci`     | `format=summary`, `level=file`                     |
| `debug`  | `format=ops`, `context=full`                       |

### Examples

Diff working tree against staging:

```console
$ merk diff
```

Diff a specific commit against its parent:

```console
$ merk diff --rev a1b2c3d4
```

Diff two commits directly:

```console
$ merk diff --rev a1b2c3d4 --rev e5f6a7b8
```

Or equivalently, comma-separated in a single flag:

```console
$ merk diff --rev a1b2c3d4,e5f6a7b8
```

Side-by-side review of one file, with word-level highlighting:

```console
$ merk diff --format side-by-side --word src/main.zig
```

CI-friendly summary of staged changes:

```console
$ merk diff --staged
3 paths staged
```

Apply the `debug` profile to see the raw diff ops with full context:

```console
$ merk diff --profile debug --rev a1b2c3d4
```

Restrict to a subtree and show only additions:

```console
$ merk diff --only-added src/parser/
```

### Errors

- Invalid values for `--format`, `--level`, `--context`, `--group`,
  `--algo`, `--show`, `--color`, or `--profile` each produce a specific
  `error: invalid <flag> '<value>'` message.
- `--rev` given more than twice: `error: --rev can be given at most twice
(comparing two trees)`.
- `--staged` combined with `--rev`: `error: --staged and --rev are mutually
exclusive`.
- An unresolvable `--rev` value distinguishes ambiguous prefixes
  (`error: ambiguous --rev '<r>' (matches multiple objects)`) from not-found
  hashes (`error: --rev '<r>' not found`).

## `merk restore`

Restore working tree paths from the index, or unstage them with `--staged`.

### Synopsis

```
merk restore [--staged] <path>...
```

### Description

Two distinct operations depending on `--staged`:

- **Without `--staged`**: overwrites the given working-tree paths with their
  currently _staged_ content, discarding uncommitted edits on disk. This is
  the merk equivalent of `git restore` / `git checkout -- <path>`.
- **With `--staged`**: removes the given paths from the staging area
  (unstages them) without touching the working tree — equivalent to `git
restore --staged` / `git reset <path>`.

At least one path is required.

### Options

| Flag       | Description                                                     |
| ---------- | --------------------------------------------------------------- |
| `--staged` | Unstage the given path(s) instead of touching the working tree. |

### Examples

Discard uncommitted edits to a file, resetting it to the staged version:

```console
$ merk restore src/main.zig
restored src/main.zig
```

Unstage a file without touching its on-disk content:

```console
$ merk restore --staged src/main.zig
unstaged src/main.zig
```

### Errors

- Any path not currently tracked/staged: `error: one or more paths are not
staged` (with `--staged`) or `error: one or more paths are not tracked`
  (without).

## `merk unstage`

Remove paths from the staging area and, unless `--cached`, the working tree.

### Synopsis

```
merk unstage [--cached] <path>...
```

### Description

This is merk's `git rm`. It stops tracking the given paths entirely:

- By default, deletes the file from the working tree **and** removes it
  from staging.
- With `--cached`, removes the path from staging only — the on-disk file is
  left untouched (equivalent to `git rm --cached`).

Every path is validated as tracked _before_ any mutation happens, so a typo
in a multi-path invocation fails cleanly without partially removing files.

### Options

| Flag       | Description                                         |
| ---------- | --------------------------------------------------- |
| `--cached` | Only unstage; leave the working-tree file in place. |

### Examples

Untrack and delete a file:

```console
$ merk unstage old_module.zig
removed old_module.zig
```

Untrack a file but keep it on disk (e.g. moving it into `.gitignore`-style
exclusion):

```console
$ merk unstage --cached secrets.env
removed (cached) secrets.env
```

### Errors

- Any path not currently tracked: `error: '<path>' is not tracked`.

## `merk mv`

Move or rename tracked files or directories, updating both the staging area
and the working tree.

### Synopsis

```
merk mv [--force] <from>... <to>
```

### Description

Behaves like GNU `mv` applied to tracked paths:

- **Single source, destination is not an existing tracked directory** — the
  source is renamed to exactly `<to>`. For a tracked _directory_ source,
  this renames the whole directory (every file underneath is re-rooted from
  the old prefix to the new one).
- **Single source, destination is an existing tracked directory** — the
  source lands _inside_ it (`<to>/<basename-of-source>`).
- **Multiple sources** — the destination _must_ be an existing tracked
  directory; each source lands inside it. (There's no sensible "rename to a
  single path" reading with more than one source.)

The full set of `(from, to)` pairs is computed and validated up front before
anything is actually moved, so a bad source later in the argument list is
caught before any earlier source has moved. Note that the move itself is
**not transactional** — each pair is applied to staging/working tree as
`mv` iterates the plan, so if one pair fails partway through, everything
already printed has already moved.

If two sources in the same invocation compute the same destination path,
the second is rejected as "destination already tracked" (from the first
move), the same as a normal destination collision.

### Options

| Flag      | Description                                    |
| --------- | ---------------------------------------------- |
| `--force` | Overwrite an already-tracked destination path. |

### Examples

Rename a single tracked file:

```console
$ merk mv src/old_name.zig src/new_name.zig
renamed  src/old_name.zig -> src/new_name.zig
```

Move a file into an existing tracked directory:

```console
$ merk mv src/util.zig src/lib/
renamed  src/util.zig -> src/lib/util.zig
```

Move several files into a directory at once:

```console
$ merk mv src/a.zig src/b.zig src/lib/
renamed  src/a.zig -> src/lib/a.zig
renamed  src/b.zig -> src/lib/b.zig
```

Rename an entire tracked directory:

```console
$ merk mv src/old_module src/new_module
renamed  src/old_module/mod.zig -> src/new_module/mod.zig
renamed  src/old_module/util.zig -> src/new_module/util.zig
```

Overwrite an already-tracked destination:

```console
$ merk mv --force src/draft.zig src/final.zig
renamed  src/draft.zig -> src/final.zig
```

### Errors

- Fewer than two positional arguments: `error: 'mv' takes at least two
paths: <from>... <to>`.
- Multiple sources with a destination that isn't a tracked directory:
  `error: '<dest>' is not a tracked directory — with multiple sources the
destination must be one`.
- A source that's neither a tracked file nor a tracked directory:
  `error: '<src>' is not a tracked file or directory`.
- Per-pair issues (absolute paths, paths escaping the repo, source ==
  destination, destination already tracked without `--force`) are reported
  by the underlying repository move operation with a specific message for
  each case.

## `merk commit`

Record staged changes as a new commit.

### Synopsis

```
merk commit -m <message> [options] [labels...]
```

### Description

Creates a new commit from the current contents of the staging area and
advances the current track to point at it. A commit message (`-m`) is
required and cannot be empty or whitespace-only.

Key behaviors:

- **Nothing to commit** is rejected in two ways: if the staging area is
  entirely empty (`error: nothing to commit (staging is empty...)`), or if
  the staged tree is byte-for-byte identical to the current track tip
  (`error: nothing to commit — staged tree is identical to CURRENT`).
- **Author identity** falls back in order: `--author` flag → `$merk_AUTHOR_NAME`
  → `$USER` → `"unknown"`; similarly `--author-email` falls back to
  `$merk_AUTHOR_EMAIL` → `"unknown@local"`.
- **Committer identity** defaults to the author's identity unless any
  `--committer*` flag is explicitly given.
- **Dates** (`--date`/`--author-date`, `--committer-date`) accept either a
  raw Unix-millisecond integer or an ISO-8601 `YYYY-MM-DD` date (interpreted
  as UTC midnight).
- **Trailers** (git-style `Key: Value` metadata lines) can come from two
  places, which are merged: any trailing `key: value` lines at the end of
  `--body` are parsed out automatically (unless `--no-body-trailers` is
  set), and any explicit `--trailer key=value` flags are appended after
  them. `--trailer` is repeatable and also accepts comma-separated
  `key=value` pairs in one occurrence.
- **Labels** (freeform scope tags) can be given as `--label a,b,c` and/or as
  trailing positional arguments — both are merged into the same list.
- **Intent** classifies the commit's purpose. Recognized values: `feature`,
  `fix`, `refactor`, `docs`, `test`, `performance`, `security`, `build`,
  `ci`, `release`, `chore`. Any other string is accepted as a custom intent.
  Default: `feature`.

### Options

| Flag                          | Description                                                                                                  |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `-m, --message <msg>`         | Commit title. **Required.**                                                                                  |
| `--body <text>`               | Extended description. Trailing `key: value` lines are parsed as trailers unless `--no-body-trailers` is set. |
| `--no-body-trailers`          | Treat `--body` as plain text; skip trailer extraction.                                                       |
| `--trailer <key=value>`       | Append a trailer. Repeatable; also accepts `key=value,key=value`.                                            |
| `-i, --intent <intent>`       | See recognized values above. Default: `feature`.                                                             |
| `-l, --label <label[,label]>` | Comma-separated scope labels. Positional args are also accepted as labels.                                   |
| `--author <name>`             | Author name. Falls back to `$merk_AUTHOR_NAME` then `$USER`.                                                 |
| `--author-email <addr>`       | Author email. Falls back to `$merk_AUTHOR_EMAIL`.                                                            |
| `--author-date <date>`        | Author timestamp: Unix-ms or `YYYY-MM-DD`. Default: now.                                                     |
| `--date <date>`               | Alias for `--author-date`.                                                                                   |
| `--committer <name>`          | Committer name. Default: same as author.                                                                     |
| `--committer-name <name>`     | Alias for `--committer`.                                                                                     |
| `--committer-email <addr>`    | Committer email. Default: same as author.                                                                    |
| `--committer-date <date>`     | Committer timestamp: Unix-ms or `YYYY-MM-DD`. Default: same as author.                                       |

### Examples

Minimal commit:

```console
$ merk commit -m "Add histogram diff algorithm"
✓ Commit created

  Hash      a1b2c3d4
  Track     main
  Type      root commit
  Intent    feature

  Message
    Add histogram diff algorithm

  Author
    Jane Doe <jane@example.com>

  Changes
    3 staged files
```

Commit with an explicit intent, labels, and body:

```console
$ merk commit -m "Fix use-after-free in diff rendering" \
    --intent fix \
    --label diff,memory-safety \
    --body "Freed source buffers were referenced after the diff loop exited."
```

Commit using trailers embedded in the body:

```console
$ merk commit -m "Add duplicate-commit prevention" --body "
Prevents committing when the staged tree matches CURRENT.

Reviewed-by: Alice
Closes: #42"
```

Commit with explicit trailer flags instead:

```console
$ merk commit -m "Refactor CLI dispatch" \
    --trailer reviewed-by=Alice --trailer closes=#42
```

Override author/committer identity and dates, e.g. for scripted imports:

```console
$ merk commit -m "Import legacy history" \
    --author "Legacy System" --author-email legacy@example.com \
    --author-date 2023-06-01 \
    --committer "Jane Doe" --committer-email jane@example.com
```

### Errors

- Missing `-m`: `error: commit message is required (-m <message>)`.
- Empty/whitespace-only message: `error: commit message must not be empty`.
- Unparseable `--date`/`--author-date`/`--committer-date`: `error: cannot
parse date '<raw>' — use Unix-ms or YYYY-MM-DD`.
- Malformed `--trailer` (missing `=`, or failing trailer validation):
  `error: trailer '<t>' must be in key=value form` / `error: invalid
trailer '<t>': <reason>`.
- Empty staging area: `error: nothing to commit (staging is empty — run
\`merk snapshot <path>\` first)`.
- Staged tree identical to the track tip: `error: nothing to commit — staged
tree is identical to CURRENT (stage changes with \`merk stage\` first)`.
- Message/body/trailer validation failures (title too long, too many
  trailers, illegal characters, etc.) are reported with a specific,
  human-readable reason for each case.

## `merk log`

Print commits reachable from HEAD with author, committer, message, and
parent information.

### Synopsis

```
merk log
```

### Description

Walks the current track's history from the tip backward and prints one block
per commit: full hash, author, committer, message title, and parent
hash(es) (or `(none)` for the root commit). Takes no flags or arguments.

### Examples

```console
$ merk log
commit a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2
author: Jane Doe <jane@example.com>
committer: Jane Doe <jane@example.com>
message: Add histogram diff algorithm
parents: e5f6a7b8c9d0e5f6a7b8c9d0e5f6a7b8c9d0e5f6a7b8c9d0e5f6a7b8c9d0e5f6

commit e5f6a7b8c9d0e5f6a7b8c9d0e5f6a7b8c9d0e5f6a7b8c9d0e5f6a7b8c9d0e5f6
author: Jane Doe <jane@example.com>
committer: Jane Doe <jane@example.com>
message: Initial commit
parents: (none)
```

### Errors

- No commits yet: `error: no commits yet`.

### Notes

- `log` currently has no filtering, paging, or range flags (`--oneline`,
  `-n`, revision ranges, etc.) — it always prints the full reachable
  history from the current track tip. Long histories should be piped
  through a pager (e.g. `merk log | less`) until built-in paging lands.

## `merk inspect`

Show the changes between two commits, or a commit and its parent.

### Synopsis

```
merk inspect [<commit-hash>] [<commit-hash>] [flags]
```

### Description

`inspect` is `merk`'s `git show` / `git diff <a> <b>` for history:

- **No arguments**: shows the current track tip against its parent, with a
  full commit metadata header (hash, author, committer, date, intent,
  labels, message).
- **One `<commit-hash>`**: shows that commit against its own first parent,
  with the same header.
- **Two `<commit-hash>` arguments**: shows the diff between the two commits
  directly (in the order given); no commit header is printed in this form,
  since there's no single "focal" commit.

Both full 64-character hashes and 8+ character prefixes are accepted, and
resolved the same way `diff --rev` resolves them.

### Options

| Flag                     | Description                                                                       |
| ------------------------ | --------------------------------------------------------------------------------- |
| `-s, --stat`             | Print a per-file change summary with totals instead of (or after) the full diff.  |
| `--name-only`            | List only the changed file paths, one per line.                                   |
| `-w, --word`             | Word-level highlighted diff.                                                      |
| `--format <fmt>`         | `unified` (default), `side_by_side`, `blocks`, `ops`, `summary`                   |
| `-a, --algorithm <algo>` | `myers`, `patience`, `histogram` (default: `histogram`)                           |
| `-U, --context <n>`      | Lines of context around changes. Default: `3`.                                    |
| `--group-by <mode>`      | `none` (default), `files`, `dirs`                                                 |
| `--filter <list>`        | Comma list restricting shown file states: `added,deleted,modified` (default: all) |
| `--path <prefix>`        | Limit output to paths starting with this prefix. Repeatable.                      |
| `--no-header`            | Suppress the commit metadata header (only applies to the 0- or 1-argument forms). |

### Examples

Inspect the current tip:

```console
$ merk inspect
commit a1b2c3d4e5f6...
Author: Jane Doe <jane@example.com>
Date:   2026-08-11 14:03:22 UTC +0000
Intent: feature

    Add histogram diff algorithm

--- src/diff.zig
+++ src/diff.zig
...
```

Inspect a specific commit by short hash:

```console
$ merk inspect a1b2c3d4
```

Compare two arbitrary commits directly:

```console
$ merk inspect a1b2c3d4 e5f6a7b8
```

Just the file list touched by a commit:

```console
$ merk inspect a1b2c3d4 --name-only
src/diff.zig
src/diff/histogram.zig
```

Change summary with totals, no header:

```console
$ merk inspect a1b2c3d4 --stat --no-header
--- src/diff.zig
+++ src/diff.zig
...

1 file(s) changed, +42 -8 lines, +0 -0 words
```

Restrict to one subtree and only show added/modified files:

```console
$ merk inspect a1b2c3d4 --path src/diff/ --filter added,modified
```

### Errors

- No commits yet (0-argument form): `error: no commits yet`.
- Invalid `--filter` value: reported via the standard filter-parsing error.
- An unresolvable commit-hash argument: reported the same way `diff --rev`
  reports ambiguous or not-found revisions.

## `merk uncommit`

Move the current track back to its parent, undoing the last commit.

### Synopsis

```
merk uncommit [--hard | --mixed | --keep] [--yes]
```

### Description

Undoes the most recent commit on the current track by moving the track
pointer to that commit's parent. `--hard`, `--mixed`, and `--keep` are
mutually exclusive and control what happens to staging and the working
tree; the default (none given) is **soft**.

| Mode             | Staging                                                                                                                | Working tree                                                                         |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| `soft` (default) | Left as-is (still holds the undone commit's changes, ready to re-commit or edit)                                       | Untouched                                                                            |
| `--mixed`        | Reset to match the parent commit's tree                                                                                | Untouched                                                                            |
| `--hard`         | Reset to match the parent commit's tree                                                                                | Reset to match the parent commit's tree (**destructive** — uncommitted work is lost) |
| `--keep`         | Rebuilt from the _current on-disk content_ of every tracked path (preserves post-commit edits as the new staged state) | Untouched                                                                            |

Only linear history is supported — `uncommit` refuses to run if the current
tip is a merge commit.

Uncommitting the **root commit** with `--hard` deletes every tracked file
from the working tree with nothing else pointing at their content; this
requires an explicit `--yes` to confirm.

### Options

| Flag        | Description                                                               |
| ----------- | ------------------------------------------------------------------------- |
| `--hard`    | Reset staging **and** the working tree to the parent commit. Destructive. |
| `--mixed`   | Reset staging to the parent commit; leave the working tree alone.         |
| `--keep`    | Rebuild staging from the current on-disk content of tracked paths.        |
| `-y, --yes` | Confirm a `--hard` uncommit of the root commit.                           |

### Examples

Undo the last commit, keeping its changes staged (default, soft):

```console
$ merk uncommit
undone         a1b2c3d4...
main is now at e5f6a7b8...

Changes from the undone commit are still staged — edit and re-run
`merk commit` when ready, or `merk restore --staged <path>` to drop
specific files back out of staging.
```

Undo and unstage, but leave the working tree files as they are:

```console
$ merk uncommit --mixed
undone         a1b2c3d4...
main is now at e5f6a7b8...

Staging now matches the parent commit's tree; the working tree is untouched.
```

Fully discard the last commit's changes, including on disk:

```console
$ merk uncommit --hard
undone         a1b2c3d4...
main is now at e5f6a7b8...

Staging and the working tree now match the parent commit.
```

Undo the very first commit ever made (destructively):

```console
$ merk uncommit --hard --yes
undone         a1b2c3d4...
main is now at  (no commits)

That was the root commit — 'main' has no commits now.
```

### Errors

- More than one of `--hard`/`--mixed`/`--keep`: `error: --hard, --mixed,
and --keep are mutually exclusive`.
- `--hard` on the root commit without `--yes`: `error: uncommitting the
root commit with --hard deletes tracked files from the working tree, with
nothing else reachable pointing at their content; pass --yes to confirm`.
- Current tip is a merge commit: `error: HEAD is a merge commit; uncommit
only supports linear history`.
- `--keep` when a tracked path no longer exists on disk: `error: --keep
needs every tracked path to still exist on disk; some were deleted since
the commit`.

## `merk write-tree`

Write the current staging area as a Merkle root. _(plumbing)_

### Synopsis

```
merk write-tree
```

### Description

A low-level ("plumbing") command that computes and prints the content hash
of the current staging area's tree structure, without creating a commit.
Useful for scripting, debugging, or inspecting what a subsequent `commit`
would record as its snapshot root, without the side effect of actually
committing.

Takes no arguments or flags.

### Examples

```console
$ merk write-tree
a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2
```

Typical scripted use — compare the staged tree root before and after a
change without committing:

```console
$ before=$(merk write-tree)
$ merk stage some_file.zig
$ after=$(merk write-tree)
$ [ "$before" != "$after" ] && echo "staging changed"
```

## Typical workflow

Putting the commands together end to end:

```console
$ merk init my-project
$ cd my-project
$ echo "fn main() void {}" > main.zig
$ merk stage .
stage    main.zig

1 path staged
$ merk status
Repository

Staged for next commit (1 path)
$ merk commit -m "Initial commit" --intent chore
✓ Commit created
  ...
$ merk log
commit ...
$ echo "// updated" >> main.zig
$ merk diff
...
$ merk stage main.zig
$ merk commit -m "Add comment" --intent docs
$ merk inspect --stat
...
$ merk uncommit --mixed   # undo the last commit, keep the edit unstaged... actually staged is reset
```
